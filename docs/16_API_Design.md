# 16 — API Design (IPC Contract)

**Related:** [03_System_Architecture.md](03_System_Architecture.md) · [06_Data_Flow.md](06_Data_Flow.md) · [08_Security_Model.md](08_Security_Model.md)

The IPC surface between webview and Rust core is the application's internal API. It is small, typed end-to-end, versioned, and security-reviewed per addition ([13] §8).

---

## 1. Principles

1. **Minimal surface** — a command exists only if the webview cannot do the work itself.
2. **Typed both sides** — Rust structs with `serde` ↔ TS types generated by `specta`/`tauri-specta` (single source of truth, drift is a build error).
3. **Commands = request/response; events = push** ([03] §3.5). No polling anywhere.
4. **Every command validates, scope-checks, then works** — in that order, always.
5. **Cancellable long operations** — token-based (search, big reads).
6. **Errors are data** — `NspError { code, message, path? }`; UI owns presentation.

## 2. TS access layer

Stores never call `invoke` directly. `src/ipc/` exposes domain services (`fileService`, `searchService`, `configService`, `sessionService`) wrapping generated bindings — mockable in tests, one place for retry/error mapping.

## 3. Command catalog (v1)

### fs
| Command | Signature (TS view) | Notes |
|---|---|---|
| `fs_read_file` | `(path) → FileContent { docId, meta: {encoding, eol, size, readonly}, text? }` | > 4 MB: returns meta, content streams via `fs:chunk` events |
| `fs_write_file` | `({ path, text, encoding, eol }) → SaveResult { mtime }` | atomic ([07] §2); self-change marker |
| `fs_create` | `({ dir, name, kind: file\|folder }) → Entry` | overwrite-guarded |
| `fs_rename` | `({ from, to }) → Entry` | |
| `fs_duplicate` | `(path) → Entry` | |
| `fs_trash` | `(path) → void` | OS trash only |
| `fs_move` | `({ from, toDir }) → Entry` | DnD backend |
| `fs_list_dir` | `(path) → Entry[]` | lazy tree expansion |
| `fs_stat` | `(path) → Meta` | |

## 4. Event catalog

| Event | Payload | Emitted when |
|---|---|---|
| `fs:chunk` | `{ docId, seq, text, done }` | streaming large read |
| `fs:changed` | `{ path, kind: modify\|remove\|rename, newPath? }` | watcher ([06] §5) |
| `fs:bulk_changed` | `{ root }` | coalesced churn ([07] §4) |
| `search:results` | `{ token, batch: Match[] }` | streaming, ~50/batch |
| `search:done` / `search:error` | `{ token, stats } / { token, error }` | |
| `config:changed` | `{ key, value }` | UI write **or** TOML hand-edit |
| `watcher:degraded` | `{ reason }` | fallback engaged ([07] §4) |
| `updater:progress` | `{ pct }` | during user-initiated update |

## 5. Error codes

`E_NOT_FOUND, E_ACCESS_DENIED, E_SCOPE, E_BINARY, E_TOO_LARGE, E_ENCODING, E_CONFLICT (mtime mismatch on save), E_IO, E_INVALID_INPUT, E_CANCELLED, E_CONFIG_INVALID`. Mapping to UX in `src/ipc/errors.ts` (toast vs dialog vs banner per code); every code has at least one test asserting its user-facing path.

## 6. Versioning & evolution

The IPC contract is internal (no external consumers) but changes are still disciplined: generated-types drift breaks the build; removing/renaming a command or event requires one deprecation minor with both paths live; the catalog tables above are updated in the same PR (CI check greps handler registrations vs this doc's command names).
